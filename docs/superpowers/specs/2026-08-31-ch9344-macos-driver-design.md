# CH9344 macOS 四路串口驱动设计

状态：已批准

批准日期：2026-08-31

## 目标

为当前机器上的 WCH CH9344（VID `0x1a86`、PID `0xe018`）实现四个彼此独立的标准 macOS 串口服务，支持波特率、8N1、RX、TX、DTR 和 RTS。开发先通过用户态 USB 工具证明协议，再实现单路 DriverKit 原型，最后发布四路串口。

## 设计决策

采用“协议验证工具 → 单路 DriverKit 原型 → 四路串口”的分阶段方案。用户态工具不是最终驱动，而是把 USB 协议错误与 DriverKit 生命周期、签名和服务发布错误分离开的可执行证据。

最终产品采用 macOS 原生架构：Swift 宿主 App 使用 System Extensions framework 安装和管理驱动；C++ DriverKit DEXT 使用 USBDriverKit 访问 USB interface 和 Bulk endpoints，并使用 SerialDriverKit 发布标准串口。`cyme --lsusb` 与 `libusb` probe 仅属于开发诊断和协议验收，不会成为最终驱动的运行时依赖。

DEXT 选择 C++ 是由 DriverKit 的公开接口边界决定的：DriverKit 服务是 C++ 类，Xcode 模板使用 C++ 与 `.iig`，`IOUserSerial` 和 `IOUSBHostInterface` 也由 C++ ABI 暴露。Swift 用于宿主 App；Rust 若用于 DEXT 仍需经过 C++/FFI 才能实现 DriverKit 服务，本项目首期不增加该边界。

暂不采用以下路线：

- 不直接从四路 DEXT 开始，因为协议、USB 异步传输和多服务发布会同时进入调试路径；
- 不把 PTY 桥接当最终产品，因为它不等价于由 SerialDriverKit 发布的标准硬件串口；
- 不修改 WCH 已签名 DEXT 的 `Info.plist`，因为它没有可验证的 CH9344 复用实现，修改也会破坏签名。

## 组件边界

### 协议核心

协议核心使用不依赖 macOS framework 的 C++17，实现：

- 逻辑端口 `0...3` 与硬件端口 `4...7` 的映射；
- 数据 TX 组帧和 RX 32 字节记录解帧；
- 芯片版本响应识别；
- UART 初始化、波特率、数据格式、DTR 和 RTS 命令编码；
- 所有输入长度、端口范围和输出容量检查。

协议核心不直接拥有 USB 设备、线程、队列或日志对象。它接受显式字节缓冲区并返回明确错误码，使同一实现可以被命令行工具和 DEXT 共用，并能用纯单元测试覆盖。

### 用户态 USB 验证工具

验证工具使用本机已经安装的 `libusb-1.0` 打开 VID `0x1a86`、PID `0xe018`，只接受 interface 0 和预期的四个 Bulk 端点。它负责：

- 输出设备、interface、端点方向和最大包长；
- 读取 4 字节芯片版本并判定 CH9344L 或 CH9344Q；
- claim/release interface，并在所有退出路径恢复资源；
- 通过命令 Bulk OUT 配置指定端口；
- 通过数据 Bulk OUT/IN 执行带超时的发送和接收；
- 对第 4 路执行可重复的二进制 TX/RX 回环测试。

工具默认执行只读的 `inspect`。会改变 UART 状态或发送数据的动作必须由明确子命令触发，避免运行诊断命令时误发数据。

### DriverKit USB transport

DEXT 匹配 `IOUSBHostInterface`、VID `0x1a86`、PID `0xe018`、configuration 1、interface 0。transport 独占四个 Bulk 端点，维护唯一的设备生命周期和异步 I/O：

- 一个连续的数据 IN 读取循环；
- 一个连续的命令/状态 IN 读取循环；
- 一个串行化命令 OUT 队列；
- 一个公平轮询四路端口的共享数据 OUT 调度器；
- 断开、挂起、恢复和错误后的统一状态复位。

USB completion 不直接执行业务重配置。completion 只归还缓冲区、记录结果并唤醒串行调度路径，避免重入和端口间状态竞争。

共享 transport 使用 DriverKit 公开的 `IOService::Create()`，从 DEXT `Info.plist` 中的四份子服务属性创建端口服务；每份属性固定逻辑端口号和唯一 TTY suffix。任何端口创建失败都必须终止本次 transport 启动并回收已经创建的端口，不能用少于四个节点冒充完整启动。

### SerialDriverKit 端口服务

每个逻辑端口拥有独立的 `IOUserSerial` 服务、RX/TX 队列和 UART 配置状态。端口对象只与共享 transport 交换以下信息：

- “端口有待发送数据”；
- “端口收到一段数据”；
- “应用了新的 baud/8N1/DTR/RTS”；
- “设备断开或 I/O 失败”。

端口不能直接访问 USB pipe。所有共享端点 I/O 都经过 transport，从结构上防止两个端口同时提交互相覆盖的 USB 请求。

由于 Apple 的 `IOUserUSBSerial` 固化了单路 TX 数据泵，四路实现不直接继承它。单路 DEXT 阶段先用自定义 transport 加一个 `IOUserSerial` 服务验证标准 `/dev/cu.*`、`/dev/tty.*` 发布；通过后再扩展到四个端口。如果公共 DriverKit API 无法从一个 provider 稳定注册多个串口服务，此阶段必须形成带构建日志和 IORegistry 证据的阻塞结论，不用 PTY 结果冒充驱动完成。

## 数据流

### TX

```text
应用写串口
  → 对应 IOUserSerial TX 队列
  → transport 公平选择一个非空端口
  → 协议核心添加 [硬件端口, lenLo, lenHi]
  → 共享 Data Bulk OUT
  → completion 释放请求并继续调度
```

单个 TX 帧的载荷不得超过数据 OUT 端点最大包长减 3。大于该限制的应用数据由 transport 分片，每片都携带自己的端口头。

### RX

```text
共享 Data Bulk IN
  → 协议核心按 32 字节记录校验
  → 硬件端口 4...7 映射到逻辑端口 0...3
  → 对应 IOUserSerial RX 队列
  → 应用读取串口
```

一个 USB transfer 可以包含多个端口的记录。解帧必须保持记录顺序，但不同逻辑端口进入各自队列。非法端口、长度大于 30 或尾部截断记录都计为协议错误，不得把未经验证的数据写入任意串口队列。

### 控制与配置

每个端口保存“期望配置”和“已应用配置”。`HwProgramUART`、`HwProgramBaudRate`、`HwProgramMCR` 等入口更新期望值，并由共享命令队列按端口串行下发。只有完整命令成功后才更新已应用值；失败时返回对应 `IOReturn`，不伪装成配置成功。

## 错误处理

错误分成四类：

| 类别 | 示例 | 行为 |
| --- | --- | --- |
| 输入错误 | 端口越界、空指针、输出容量不足 | 协议核心立即返回错误，不执行 USB I/O |
| 协议错误 | RX 长度大于 30、尾帧截断、未知端口 | 丢弃本批次中不安全的记录，增加计数并继续下一次读取 |
| USB 暂态错误 | 超时、短写、pipe stall | 有界恢复；保留端口隔离，不无限重试 |
| 设备生命周期 | 拔出、claim 丢失、系统停止 DEXT | 取消请求、唤醒等待者、将四路统一标记离线并释放资源 |

所有等待必须带超时。析构或 `Stop` 不依赖仍可能到来的 completion 才能完成，避免卸载时永久阻塞。

## TDD 策略

每个生产行为必须先有一个因该行为尚不存在而失败的自动化测试。执行顺序固定为：

1. RED：编写一个最小行为测试并运行，确认它以预期断言失败；
2. GREEN：编写使该测试通过的最小实现；
3. REFACTOR：只在全绿后消除重复或改名；
4. VERIFY：运行完整相关测试、构建和 `git diff --check`；
5. COMMIT：只提交该阶段涉及的显式路径。

主分支上的阶段提交保持可构建、测试全绿。RED 证据记录在阶段验证文档或终端记录中，不通过提交一个已知失败的主分支状态来证明 TDD。

测试分三层：

- 纯协议测试：每次提交都运行，无硬件依赖；
- USB 集成测试：需要设备，验证端点、版本、命令和第 4 路回环；
- DEXT 系统测试：验证激活、IORegistry 绑定、节点数量、termios 行为和四路隔离。

## 当前硬件验收矩阵

| 能力 | 第 1～3 路 | 第 4 路 |
| --- | --- | --- |
| 节点发布 | 必须通过 | 必须通过 |
| 独立 baud/8N1 | 软件与 USB 命令验证 | 软件、USB 命令与回环验证 |
| TX 路由 | USB 帧验证 | USB 帧与回环验证 |
| RX | 不宣称物理通过 | TX/RX 短接回环必须通过 |
| 跨端口隔离 | 必须无误投递 | 必须只回到第 4 路 |
| DTR/RTS | 命令编码/下发 | 命令编码/下发；当前不含电平验收 |

## 阶段与提交边界

每个阶段独立审查、验证和提交，不自动推送：

1. 工程基线：`chore: 初始化 CH9344 macOS 驱动工程`；
2. 现状评估：`docs: 记录 CH9344 驱动现状评估`；
3. 设计规格：`docs: 设计 CH9344 macOS 四路串口驱动`；
4. 实施计划：`docs: 制定 CH9344 协议验证实施计划`；
5. 协议核心：按端口映射、TX、RX、命令编码等最小行为拆分 `feat:` 提交，每个提交同时包含先写的测试和最小实现，并保持全绿；
6. 用户态工具：`feat:` 提交端点发现、芯片识别、配置与 I/O；
7. 硬件证据：`test: 验证 CH9344 第四路硬件回环`；
8. 单路 DEXT：`feat: 实现 CH9344 单路串口驱动原型`；
9. 四路 DEXT：`feat: 发布 CH9344 四路串口服务`；
10. 系统验收：`test: 验证 CH9344 四路串口隔离`。

若某阶段被平台能力或硬件条件阻塞，只提交调查文档和可复核证据，不提交伪实现，也不把后续阶段标记完成。

## 非目标

首期不实现：

- CH348 或其他 WCH PID；
- GPIO、RS-485 扩展模式、硬件流控和 9-bit 模式；
- 面向第三方机器的签名、公证、安装器和自动更新；
- 第 1～3 路的物理 RX 回环；
- DTR/RTS 的引脚电气测量。

## 完成标准

只有同时满足以下条件，才能宣称首期驱动完成：

- DEXT 在当前机器成功激活并绑定 `0x1a86:0xe018`；
- 系统稳定生成四对 CH9344 `/dev/cu.*` 和 `/dev/tty.*` 节点；
- 四路可独立打开、关闭和设置 baud/8N1；
- 第 4 路在 TX/RX 短接条件下通过二进制回环；
- 第 4 路 RX 不被投递到第 1～3 路；
- DTR/RTS 命令编码和 USB 下发通过自动化或可复核集成验证；
- 拔插后节点和状态能够正确恢复；
- 全部协议测试、构建、相关集成测试和格式检查通过。

协议 probe 完成、单路 DEXT 构建成功或单路节点出现，都只代表中间里程碑；在上述全部条件满足前，不宣称“最终驱动完成”。
